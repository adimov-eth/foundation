# Foundation — Architectural Deep Dive

## TL;DR (what it is in 5 sentences)

Foundation (`@here.build/foundations`) is the open-source extraction of here.build's production substrate: ~124K LOC of TypeScript across **17 workspace packages** (1 `plexus` + 11 `arrival/*` + 5 `common/*`, verified by `find … package.json` and `pnpm-workspace.yaml:1-4`) in a pnpm+turbo monorepo, built around two flagship systems — Plexus, a reactive CRDT engine over Yjs, and Arrival, a sandboxed-Scheme stack for agentic work — plus shared `common/*` infra. Its load-bearing architectural seam is literal and verified: an Arrival program *is* a Plexus CRDT document (`Project extends PlexusModel`, `ArrivalChain extends Plexus<Project>`, arrival-chain/src/project.ts:141, arrival-chain/src/arrival-chain.ts:18), so collaborative source, deterministic replay, and content-addressed inference all interlock through one synced Yjs doc. The whole thing is genuinely a working library with deep battle-scars and large behavioral test suites that — contrary to CLAUDE.md's cautions — install, typecheck, build, lint, and test green on this machine **when invoked per-package via direct `vitest`/`tsc` (and turbo via a PATH-shim)**; the *documented* `corepack pnpm test`/`turbo run test` entrypoint itself fails in this sandbox because no standalone `pnpm` is on PATH (see Mechanical State). What is real is the *substrate*: the interpreter, the CRDT, the content-keyed inference cache, the provenance flight-recorder, the source-to-source compiler, the MCP tool tiers. What is aspirational is concentrated in three places: the security/"sandbox" guarantee (the code itself retracts the framing and pins open DoS vectors), the studio product (absent from this repo entirely), and the "fragmentation hypothesis" thesis (an honestly-labeled, untested working hypothesis whose headline number has no harness).

## The Two Systems and the Seam Between Them (plexus, arrival, and Project-as-PlexusModel)

**Plexus** is the collaborative-state substrate: a reactive CRDT engine that turns plain TypeScript classes into Yjs-backed entities via stage-3 `@syncing` decorators. The adversarial review confirmed the core mechanic precisely: `@syncing('Name')` (plexus/src/decorators.ts:80-108) stamps `__type__` on the prototype via `Object.defineProperty(target.prototype, "__type__", ...)` (decorators.ts:96) and registers the class in a global `entityClasses` map (plexus/src/globals.ts:3, decorators.ts:106); field decorators write a per-field `kind` into schema metadata (decorators.ts:535-541, ensureSchema at :504-509); and `createHandlers` (decorators.ts:269-490) returns exactly the `{get, set, init}` triple that replaces the declared accessor. **Verdict: confirmed.**

The design's signature move — and what makes the README's "native snapshotting" claim *partly* true — is that `PlexusModel` instances hold **no own data fields**; all per-instance state lives in an external WeakMap (`internalsStore`, plexus/src/PlexusModel.ts:61), read back via `getInternals` (:77-79). Here the adversarial verdict **softened the claim to partial**: the WeakMap structure is verified, spread (`{...entity}`) works because schema accessors are marked `enumerable:true` (PlexusModel.ts:159-188), and `JSON.stringify` works via an explicit `toJSON()` hook (PlexusModel.ts:356-358). But `structuredClone` is **refuted** for the common case — the repo's own test (plexus/src/__tests__/test-snapshot.test.ts) declares a `@syncing.list accessor tags` field (:8) and exercises `structuredClone(p)` inside a try/catch that prints the thrown `'[object Array] could not be cloned'` (:17-19). So "native snapshotting just works" holds for spread and JSON-via-hook, not for structuredClone on container fields. State this honestly to anyone citing the README.

Entity identity is a reversible content-keyed UUID: `encode(clientId, clock)` packs the Yjs address into a prefixed, Feistel-scrambled base63 string (plexus/src/crdt-uuid.ts:153-187), and `decode` is its exact inverse, fuzz-tested with fast-check (plexus/src/__tests__/0-foundations/crdt-uuid.test.ts:55-62). This is what makes `deref` an O(1) WeakRef cache hit (plexus/src/deref.ts:42-47) or an O(log n) `Y.getItem`→`findIndexSS` binary-search StructStore lookup (deref.ts:58-68; yjs find→findIndexSS is a documented binary search). **Verdict: confirmed.** One materialization subtlety the review nailed: the UUID is minted by `encode`-ing `doc.clientID` plus a *predicted* next clock (`Y.getState`, PlexusModel.ts:562) just before `typeMap.set(uuid, element)` consumes it (PlexusModel.ts:571) — correct only because the bare `Y.XmlElement` is inserted attribute-free, with schema attributes written *after* the insert (:583+). **Verdict: confirmed.**

Two adversarial corrections matter for accuracy:

- **Reactivity decoupling from MobX: partial.** The core claim is verified — Plexus core only calls `trackAccess`/`trackModification` against a mutable `trackingHook` (plexus/src/tracking.ts:119-162); MobX integration populates it with per-field atoms (plexus/src/mobx/index.ts:13-38); `mobx` is an optional peer dep. But the trailing gloss "yjs is a peer/dev dep, *not* a runtime dep" is **refuted**: yjs is used at runtime pervasively (31 `Y.*` sites in Plexus.ts alone, e.g. `new Y.Doc({gc:false})` at plexus/src/Plexus.ts:289, `Y.applyUpdate`/`Y.encodeStateAsUpdate` at :309). A peer dependency *is* a runtime dependency provided by the host; the "single shared instance" invariants at Plexus.ts:570,604 exist precisely *because* yjs runs in core.
- **In-place collection diffing: refuted.** This is the most important correction. The map said reassignment does "granular add/delete via setDifference" against the Y container. Adversarial reading shows `setDifference` only drives **child parent-pointer bookkeeping** (orphan/adopt). The actual Y.Array write is `yjsArray.delete(0, length)` then `push(...)` — a wholesale clear-and-repush (plexus/src/proxies/materialized-array.ts:646-647), with an explicit `// todo optimized update strategy` at :732. The Y.Map write is `clear()` then per-entry `set()` (plexus/src/proxies/materialized-map.ts:372-381). What **is** true: the Y container *node identity* is preserved (the container is reused, never recreated — array:123/133, map:47/57), and the array has an equality short-circuit (:617-619). The map assign has **no** short-circuit. So "diffs in place against the underlying Y.Array/Y.Map" is marketing; the reality is clear-and-repush onto a reused node.

The rest of Plexus's heavy machinery is confirmed and well-tested: **child ownership** is DOM-style exclusive via symbol protocols with validation strictly before mutation (validate→emancipate→re-adopt, PlexusModel.ts:440-450, 370-398, 756-809; **confirmed**); **undo/redo** is real Yjs `UndoManager` with a 500ms capture window and a custom `deleteFilter` that protects entity shells and pre-materialization "creation content" via a recorded `materializationClock` boundary (Plexus.ts:403-445, 431-438; producer at PlexusModel.ts:653-655; **confirmed**); **liminality** uses a separate shadow `Y.Doc({gc:false})` (Plexus.ts:289) with origin-routed forwarding that holds gesture writes off main (`if (origin === LIMINAL_ORIGIN) return`, :319), commits as one atomic merged delta (extractCommittedDelta → `Y.mergeUpdates`, one undo step) or reverts, and broadcasts peer preview over awareness — fully wired, not inert (Plexus.ts:289-348, 709-815, 892-930; **confirmed**).

**Arrival** is the sandboxed Scheme interpreter (~24K LOC) the rest of the stack builds on: a generator-based flat-trampoline evaluator (`run` at arrival/arrival/src/eval/evaluator.ts:677) with real TCO (a Bounce/tail-tower-collapse protocol), three composable resource bounds (AbortSignal + wall-clock `budgetMs` at the TICK boundary; a per-run heap meter), purity doors, and a read-only interop membrane.

**The seam.** The verdict here is unambiguous and the strongest structural fact in the repo: **built and load-bearing.** `Project extends PlexusModel<null>` decorated `@syncing("ArrivalChainProject")` (arrival-chain/src/project.ts:141); `ArrivalChain extends Plexus<Project>` is a literally empty class body inheriting bootstrap/connect/root (arrival-chain/src/arrival-chain.ts:18). `Project.files` is a `@syncing.child.map<string, Program>`; each `Program` owns a `@syncing.child.list<ProgramVersion>`; `ProgramVersion.source` is a `@syncing` string — the entire source filesystem is CRDT state, materialized into `Y.XmlElement`/`Y.Map` in a `Y.Doc`. The deterministic run reads source straight out of the CRDT (`project.files.get(path).versions[idx].source`, arrival-chain/src/loader.ts:302-321), pinned by a `versionSet` snapshot recorded *on* the CRDT (`Run.versionSetJson`, arrival-chain/src/run.ts:118; captured by `Project.captureVersionSet`, project.ts:276). The **deliberate boundary**: the inference plane (`#infer: InferStoreLike`) is a private, *non-synced* field (project.ts:150-168) — keeping inference out of the CRDT is exactly what lets the system claim a run is a pure function of the project's files.

**The collaborative leg is verified, but with a precise scope caveat.** There IS a cross-package two-doc integration test — `arrival-chain/src/__tests__/plexus-over-ws-direct.test.ts` — which stands up a real `WebSocketServer`, bootstraps `docA` (`Plexus.bootstrap(rootEntity, …)`), `connect`s `docB` (`Plexus.connect(docB)`) over `y-websocket`, locally constructs a child entity on one peer, and asserts cross-doc field updates propagate to the other peer's JS reads. **But the test's own header is explicit**: it is a "**control** for the Plexus mechanics our Program/Project entities depend on … **Minimal entity** (cell + root with a child.map), no cache or program methods." It exercises a *Project-shaped* schema (`@syncing.child.map` of `@syncing accessor` entities) under genuine two-peer sync — *not the literal `Project`/`Program`/`ProgramVersion` classes*. So: multi-peer CRDT sync of the entity *shape* Arrival uses is **directly tested** (this closes most of the old "verified only by composition" caveat); end-to-end collaborative editing of the actual `Project` document, and the `y-websocket` publish path in `runPipeline` (arrival-chain/src/runner.ts:64), remain **unexercised by a dedicated test** — inferred from this control + single-doc Arrival tests, not proven on the production entity classes.

## The Arrival Stack End to End (interpreter → chain → inference → provenance → view → mcp)

A package-orientation note up front, because the most-cited subsystem spans two packages: **the inference plane (the `InferStore`, `keyOf`, the five provider backends, `_shared.ts`, the "determinism is the warrant" doc) lives in `arrival/arrival-inference/`**, NOT in `arrival-chain`. `arrival-chain` is the *orchestrator*: it depends on `arrival-inference` (package.json `@here.build/arrival-inference`), binds an `InferStore` into the CRDT `Project` (`#infer: InferStoreLike`), and owns the `(infer …)` *routing* (`inferAndWait`, `inferIdentityKey`) — but the store, cells, content-keying, and disk-cache contract are all `arrival-inference`. The data flow, all source-verified:

**1. Source → env.** `Project.run(source)` builds a sandboxed Scheme env via `buildArrivalEnv` (arrival-chain/src/project.ts:64), which lowers `arrivalCapabilities()` through a C3-linearized capability DAG (`assembleEnv`, kernel.ts:233) and appends `arrivalLoaderCorePack` **only when a loader is granted** — a loader-less env has no `require` symbol at all. `capability-scoping.test.ts` proves "the membrane IS the capability list": a utils-only env binds `string-dedent` but `(infer …)` throws unbound until `arrivalInferCapability` is added (capability-scoping.test.ts:34-50).

**2. Capabilities as the vocabulary.** Each `EnvCapability` is a module singleton whose `lower()` zod-validates config and produces a kernel pack; `apply(env)` binds each verb via `env.defineRosetta` — **the membrane**. `createRosettaWrapper` (arrival/arrival/src/rosetta.ts:351) runs `schemeToJs` on every arg (unwrapping SchemeString/Bool/JSObject/pairs/vectors to plain JS), calls the host fn, then `jsToScheme` on the result with stamped provenance. **Verdict: confirmed.** The `infer` verb itself lives in `arrival-scheme-env-infer` (arrivalInferCapability), calling a host-injected `InferFn`; MCP is **inert by default** — without a host `McpEffectResolver`, `mcp/call`/`mcp/list` route to `inertMcpResolver` which throws a teaching error, never a silent no-op or live network call (arrival-scheme-env-infer/src/mcp.ts:134-135; resolved via `?? inertMcpResolver` at :321,333,368; **confirmed**).

**3. Evaluation under a trace tap.** `Project.run` returns a `RunHandle` thenable synchronously while evaluation runs async (project.ts:119-138); user forms are exec'd form-by-form under an optional `EvalTrace` tap. The preamble (`BUILTIN_PREAMBLE`, project.ts:1059) — list/dict helpers, the `s/` schema DSL, and the superpowered-define macros (`define/overridable`, `define/exposed`, `define/mcp`) that lower to plain `(define name (<rosetta> …))` — is non-trivial Scheme logic living inline as a template string.

**4. Inference plane.** Every `(infer …)` routes through `inferAndWait` (arrival-chain/src/project.ts:410), the central infer membrane: it consults two short-circuit maps (tweaks, then effectLog) **before** any backend call (project.ts:417-427), then a single-flight `InferStore` cell. `InferStore` (arrival-inference/src/infer-store.ts) keys each call on `JSON.stringify([model, prompt, schema, cacheKey])` via `keyOf` (infer-store.ts:71-72) — the **concrete model id, not a tier** — with ref-counted abort and an optional cross-restart disk cache. `arrival-inference` owns five provider backends (anthropic/openai/openrouter/ollama/vercel under arrival-inference/src/backends/) reduced to one shared `ChatProtocol`+driver (arrival-inference/src/backends/_shared.ts). **Import-surface verified:** `arrival-inference/src/` imports from `@here.build/arrival` only `schemeToJs` (entity-middleware.ts:12) and `AString` (infer-string.ts:25) in non-test code — **never the evaluator** (a grep for evaluator/`run` imports against arrival returns nothing). Its `package.json` deps are the AI SDKs + `@here.build/arrival`, no plexus, no arrival-chain. This is the determinism-boundary import discipline, and it holds. **(confirmed)**

**5. Effect membrane.** All three external-effect kinds (infer / http+sql data / mcp) cross **one** record+replay membrane keyed in arrival-chain/src/effect-log.ts, and the ordered effect-key sequence is stored on the synced `Run`/`Hypothesis` (`@syncing.list effects`). Data effects (http/sql) are real but **inert absent a host resolver** — `inertDataResolver` throws a teaching error, never live IO; the file's own header (data-effects.ts:17-23) states the verbs are "INERT BY DEFAULT … executing one throws a teaching error … it never silently no-ops, and it never reaches a network or a database." **Honest gap:** http/sql effect *keys* are defined but emission is deferred to future "A3" builtins; only infer and mcp planes are exercised in live code paths today (http/sql appear only in tests).

**6. Provenance capture.** `EvalTrace implements EvalTap`; the evaluator drives `tap.enter(code, parent, ctx.tail)` (arrival/arrival/src/eval/evaluator.ts:2454), and the project layer stamps points (`markProvenancePoint`/`markInferCached`/`bindTask` per infer, project.ts:435-455). Analysis builders (statechart, region tree, flow graph, slicer) read finished traces.

**7. View.** `arrival-chain-view` is a deterministic source-to-source compiler projecting a Scheme string to legible JS/Python/type-faithful TS. **Naming surprise:** despite the package name and a declared `@here.build/arrival-chain` dependency, `src/` never imports arrival-chain — the only runtime deps are `arrival-sweet` (parser) and `lexical-namer`. The "chain" coupling is conceptual (it consumes a Scheme *string*, not a chain object).

The orchestration keystone is `arrival-chain` (~9.2K source LOC against ~13.5K test LOC, 100 test files / 661 `it`-blocks). `runner.ts:runPipeline` (the Node-only entry) bootstraps an `ArrivalChain`, takes `chain.root` (the CRDT Project), binds an InferStore, populates the synced files map, and runs the entry — the seam used end-to-end.

## Determinism, Content-Addressing & Replay

This is the most important place to separate what holds from what is asserted. The adversarial verdict: **built and load-bearing as a replay/memoization architecture — but it is a determinism of REPLAY and CACHE-IDENTITY, not of the model.** Two claims are bundled, and only the first holds unconditionally.

**What holds (verified):**
- A run is a pure function of the project's source files for the **default path**: the synced model holds only source (project.ts:148), the InferStore is non-synced (project.ts:159), and the sandbox env *deletes* host-reaching verbs at the source so a program cannot read wall-clock or randomness — `eval`/`load`/`new`/`set-obj!` simply do not exist, and unbound symbols throw rather than falling through to JS globals (inference-env.ts; sandbox-escape.test.ts asserts `(eval (quote +))` throws Unbound; **confirmed**). The Scheme stdlib binds no `random`/`current-time`/`Date.now`.
- `InferStore` single-flight + content-keying is real and tested against deterministic stubs (cache-key.test.ts; `replay-determinism.test.ts` adversarially proves content-addressed replay survives AST rewrites, that a re-pointed model token *misses* the log, and SQL data-drift replays the recorded row — project.ts:410-474; **confirmed**).
- The effect-log is the explicit non-determinism boundary; binding the full recorded log on replay yields zero external hits.

**What is asserted, not enforced:** the "deterministic" framing is the cache's **warrant**, not a property the model-call path guarantees. The code is honest about this: the InferStore doc literally says *"Determinism is the warrant: a run is a pure function of the body, so a cached completion equals a fresh call's"* (arrival-inference/src/infer-store.ts:19-21). On a cache **miss**, the model call is non-deterministic by construction — **no seed is sent to any backend** (grep across arrival-inference/src/backends finds no `seed` field), temperature is omitted unless the program set it (backends/anthropic.ts:78, backends/_shared.ts:567-570), and `maxTokens` is deliberately excluded from the key so the same content with a different cap serves the same cached completion. Determinism is achieved by *memoizing an admittedly stochastic process*, not by making it deterministic.

**Where non-determinism leaks by design and is documented:**
- **MCP** is the explicit hole: `mcpEffectKey` is **positional** (`effectKey("mcp", [inferenceId, server, n])`, arrival-chain/src/effect-log.ts:122-123), not content-keyed, because an MCP read's result depends on the server's hidden mutable state (the rationale comment is at effect-log.ts:113-121). Replay verifies alignment and stops on divergence rather than pretending purity. **Confirmed.**
- **Purity-breakers in `Project.run`'s own signature:** `opts.tweaks` injects brand-new counterfactual values, `opts.resolveOverride` swaps `define/overridable` bindings, and host-injected data/mcp resolvers reach live IO (project.ts:334-397). Each carries a teaching docstring, but the "pure function of files" slogan must not be taken unqualified.
- Content-param honesty rests **outside** `keyOf`: tools/temperature are folded into `cacheKey` by `inferIdentityKey` (arrival-chain/src/infer-kernel.ts:298-318) before reaching the store, because `keyOf` whitelists only `[model,prompt,schema,cacheKey]` (infer-store.ts:71-72). **This seam is now coverage-checked:** there are exactly two in-repo `(infer …)` routing paths, and *both* fold through `inferIdentityKey` before the key reaches `keyOf`/`store.get` — `inferAndWait` (project.ts:416, feeding the folded `key` into the tweak/effect/cell lookups) and `makeInfer` (chain-env.ts:185→`store.get({…}, idKey)` at :188-197). A grep for `store.get(` / `.infer.get(` in non-test source finds only the chain-env.ts:188 site, which receives the folded `idKey`. So no in-repo caller reaches the store with an unfolded key. The risk the comment warns about (infer-kernel.ts:302-304: "a param NOT folded here would silently serve a stale completion") is real for a *future external caller* that varies tools/temperature without folding — it is a documented public-API contract, not a live bug in this repo.

Mechanically, the abort budget and heap meter that bound runaway runs are verified: `run()` fast-fails a pre-aborted signal *before* allocating trampoline state, then checks `signal.aborted` and a `performance.now()` deadline at the 1000-iter/5ms TICK boundary, throwing `SchemeError(/budget/)` on overrun (evaluator.ts:677-693, 882-917; **confirmed**). One **partial** correction: "every collection op funnels through `to_array`" is overstated — `append` never touches `to_array` at all (it splices via `Pair.append`), and `map` reaches `to_array` via a bare call that drops `this` so the meter goes uncharged; only `filter`/`join` use `.call(this,…)` and are actually metered (stdlib.ts:341-356,1691,1798). The architectural story (wall-clock can't preempt a native pass; `to_array` is a per-element-metered choke point) is true for `filter`/`join`, but the blanket enumeration is wrong for `append`/`map`.

## Provenance & Reverse Execution (what uneval/slice actually computes)

The adversarial theme verdict is sharp and worth stating plainly: **"reverse-chain slicing" is TWO different mechanisms wearing one name**, and the emitted re-runnable program is **narrower than its own prose**.

1. The re-runnable program (`buildSlice`/`uneval`) is **NOT a backward dataflow slice over the trace**. It is a **static backward reference-closure over top-level `define` names**, anchored on the run's **output form**, deliberately *ignoring* the dynamically-computed provenance set. The code's own header documents this as a *correction* after an adversarial swarm proved the provenance-cone approach unsound (the cone can't name the value's own binding form or pure-combinator consumers like `string-append`/`if`/`list` between reads and output). `buildSlice` seeds from the symbols the output form references, then keeps every top-level `define` reachable by reference to a fixpoint (arrival-provenance/src/slice.ts:7-16, 241-261). **Confirmed.**

2. A genuine dynamic backward dataflow slice **also** exists: per-value `provenance` Sets minted at boundaries by `computeProvenance` (arrival-provenance/src/trace.ts:88-147), plus `backwardCone`/`flowBackwardCone` graph reachability. It is real and used — but for **highlighting / cones / effect-invalidation / attestation**, *not* to construct the emitted program. `forwardCone` drives effect-log cache invalidation (arrival-chain/src/effect-log.ts:291).

So `uneval` is a real, **sound-by-construction** program-slice (a closed subset of forms that already ran, re-runnable) **joined** to a real dynamic point-cone. It is neither a render heuristic nor the "least slice / Galois uneval" the comments invoke. Granularity is **top-level form** — a superset of the least slice; intra-form minimal slicing is explicitly deferred (arrival-provenance/src/uneval.ts:12-14). The soundness is *empirically validated, not just asserted*: ~32 combinatorial property tests + ~12 cases slice, append a terminator, re-run in a fresh project, and assert `deepEqual(rerun, original)` while pruning injected noise (slice-property.test.ts:45-71, slice.test.ts:31-152). **Confirmed.**

Two honesty notes: (a) `buildUneval`'s `uneval()` closure is the **one** place this "never drives the evaluator" package *does* re-enter the engine — it runs the selector as a fresh tapped step, mutating the live env (`env.set('result', …)`) and growing the trace (uneval.ts:89-92); `buildSlice` proper is pure. (b) The README's only code example is **broken** — it imports and calls `computeProvenance(trace)`, but `computeProvenance` is a private `(inv, trace)=>Set` in trace.ts, not exported and not callable that way.

The analysis stack is otherwise dense, working, and battle-scarred: `Invocation`/`NodeRecord` were deliberately de-MobXed to plain objects to fix a real 1.3GB-heap-dump OOM in a 46k-invocation TCO loop (trace.ts:32-46); field-point minting is idempotent to cap an 80k-field-point blowup (trace.ts:88-147). The flagship subsystems (statechart, region-fold parity, flow-graph) are real and tested — but **all** their substantive tests live in the sibling `arrival-chain` package, not in `arrival-provenance/src/__tests__` (which ships only 2 unit tests). One self-described dormant field: `tailPosition` is captured as ground truth but read by nothing (loop detection is structural via `hasSelfAncestor`); the code admits it is kept-for-later (trace.ts:193-201).

## The Studio: Shipped Substrate vs Unshipped App (be blunt)

**There is no studio in this repo.** Blunt verdict: **substrate, no studio.** The workspace is **17 substrate packages** (1 plexus + 11 arrival/* + 5 common/*), all `@here.build/*` (pnpm-workspace.yaml:1-4, enumerated under `plexus/`, `arrival/*/`, `common/*/`). A filesystem sweep finds **zero UI artifacts**: no `.tsx`/`.jsx`/`.html`, no react/vite/next dependency, no `*studio*` directory, no app/server/bin entrypoint. (Correction to an earlier draft: `hono` is a **regular `dependencies` entry** of `arrival-mcp` — arrival-mcp/package.json `dependencies.hono = "4.12.0"`, *not* a devDependency — though it is near-vestigial: its sole `src/` use is `import type {Context} from "hono"` in the inert `resources/index.ts:7`.)

Every one of the ~40 "studio" references is a comment, package description, test name, or doc note pointing **outward** to an external, private host application that *consumes* these packages. The packages are deliberately host-agnostic seams: `infer-store.ts:23-27` itself states "This lives in arrival-inference (not the OSS runner) so every host shares ONE plane: the headless `evalBody` path, the browser's `POST /infer` SSE path, and the saas Durable Object…" and ":200-212" describes the browser studio's SSE-backed store as one possible host *not in this repo*; `plexus/src/telemetry.ts:11-14` says Plexus is "consumed by here.build studio + (eventually) external users"; `ActionTool.ts:237` carries copy "Shown in the studio UI as live AI presence"; `trace-to-flow-graph.ts:3` references a "React Flow + elkjs renderer in the host studio."

The shipped presence code is the generic `PlexusAwareness` (plexus/src/awareness.ts:80, a fork of y-protocols/awareness); the product-specific `StudioAwareness` subclass is closed and absent from all shipped `*.ts`, recovered only as a historical usage note (docs/40-history/prior-audit/awareness-usage-example.md). ## What's Genuinely Novel vs Conventional

**Genuinely novel (or rare in combination):**
- **The CRDT-UUID-as-physical-address codec.** Making the entity identity a reversible Feistel-scrambled encoding of the Yjs `{clientId, clock}` so `deref` is O(1)/O(log n) with no side index is a clever, content-keyed identity scheme (crdt-uuid.ts).
- **Project-as-CRDT-document with inference held outside the doc.** The deliberate decision that source + effect-key trace + version pins are synced while *values* flow through a host-local content-addressed plane (the `InferStore` in arrival-inference, bound non-synced into the CRDT `Project`) — and that this is precisely what makes "run = pure function of files" coherent — is a genuinely thoughtful architectural seam (project.ts:150-168; infer-store.ts:23-27).
- **Security/purity-by-deletion as a *design stance*** (whatever its security weaknesses): omitting two whole R7RS feature families (dynamics + mutation) and justifying it by *provenance soundness* ("mutation/dynamic extent falsifies provenance") rather than sandbox safety is unusual and internally coherent (purity doors, core.ts).
- **The static-reference-closure reverse slice**, arrived at *after* an adversarial swarm proved the obvious provenance-cone approach unsound, and validated by re-running the emitted program to `deepEqual` — sound-by-construction reverse execution is rare and the empirical validation is real (slice.ts, slice-property.test.ts).
- **The two-doc shadow/main liminality architecture** with origin-routed forwarding, append-only undo shells, and content-addressed genesis entities for conflict-free concurrent spawn — sophisticated CRDT engineering, the dominant source of Plexus complexity.

**Conventional (competently executed, not new):** the LIPS-derived Scheme reader; the five LLM backends reduced to a shared chat protocol (sensible, standard); the content-keyed single-flight inference cache (a memoization pattern); the C3-linearized capability DAG (Python MRO); the `EnvCapability`/rosetta membrane (a fairly standard host-binding pattern); the source-to-source emitters in chain-view (good golden-file discipline, conventional compiler shape).

**Genuinely novel as a *claim* but unproven:** the fragmentation hypothesis itself. If true and measured it would be notable; as shipped it is an untested heuristic.
